## Import Center Completion (this stage)

Accepted local SHA: see `git log` on branch `import-center-completion` (first commit message starts `Import Center Completion`), based on `main @ 43db934`.

**Substrate**: one governed registry (`src/server/imports/target-registry.ts`, unchanged contract, extended with an optional generic `rows`/`rowsTruncated` field and a shared `ImportAdapterError` for classified-error propagation through the generic dispatch path). `src/app/api/imports/dry-run` and `/execute` still call the Analytics service directly (precise, pre-existing error-code mapping) and dispatch through `getImportTarget()` for any other registered module - proven with two real targets, not a hypothetical single-target registry.

**Adapters** (`listImportTargets()` after `registerImportTargets()`):
- `analytics` - preserved, extended (below). Preserved without behavior change: deterministic row-identity matching, batch-level source-hash idempotency, Content/Partner-Account matcher contracts, `ANALYTICS_ROW_CLASSIFICATIONS` (all nine original values still mean exactly what they meant).
- `contract_bundle` - new. Bulk Partner/Vendor + one Partner Account + Agreement-draft-to-be, one row per bundle, via `src/server/imports/contract-bundle-import.ts`. Every mutation goes through the EXISTING `createCounterpartyFromOnboarding` (Step 14B.1) - no bespoke Partner/Vendor/Agreement write anywhere in this file. Deliberate, documented scope decisions for this stage: (1) one Partner Account per row; (2) NO restricted/KYC/payee-identity columns at all - a sheet with any PAN/Aadhaar/GST/bank/IFSC/UPI/passport/KYC-looking header is rejected wholesale (`RESTRICTED_FIELD_REJECTED`) before a single row is read; KYC continues to be captured afterward, per Agreement, through the existing `SecureKycDialog`/KYC service, never through this bulk path; (3) no bundle-specific resume endpoint - each row's own onboarding step-ledger is already resumable by re-executing the same bundle (same deterministic row `clientRequestId`), so a second resume mechanism would only duplicate that orchestration; (4) a likely-duplicate row is never force-created - it is reported (`AMBIGUOUS`) for the actor to resolve through the ordinary, interactive Agreement-led onboarding screen, which can supply the acknowledgement + reason a STRONG duplicate needs; a bulk import never supplies that on the actor's behalf.
- Intentionally unsupported / future adapters (classified during inspection, not built): Payables/Invoices/Payments bulk import, Operations Task/Reminder bulk import, Vendor-only bulk roster import. None of these had a real, working minimal implementation to extend (unlike Analytics/contract-bundle); adding them now would be "arbitrary targets just to increase the count," which the spec explicitly warns against.

**Governed UX** (`src/features/imports/ImportCenterTabs.tsx` -> `ImportCenterWizard.tsx` + `ImportHistoryPanel.tsx`, replacing the prior bare `ImportCenterPanel.tsx`): Choose Data → Upload (drag/drop + picker, remove/replace, exact accepted types) → File/Sheet Preview (`/api/imports/preview`, bounded sample rows, duplicate/empty header + trailing-blank-row detection, all read-only) → Mapping (conditional - shown only when a sheet is unrecognized or has ignored columns; an unrecognized sheet blocks with an actionable message, since this stage does not implement free-form column remapping - see scope note below) → Validation & Diff/Review (bounded per-row detail, outcome-group counts, mandatory acknowledgement checkbox, Import disabled until acknowledged AND the file is unchanged since review) → Import (explicit, re-authorizes/re-validates server-side regardless of the client's own prior dry-run) → Results (counts, row outcomes, inline resume prompt when rows are quarantined) → History (`/api/imports/batches`, module-aware, attempt history, resume from a quarantined batch).

**Scope decision - Mapping is informational, not a free-form remapper**: the existing Analytics adapters recognize a sheet by matching a FIXED set of header aliases per platform template (all-or-nothing per sheet), not by letting an actor redirect an arbitrary column to an arbitrary canonical field. Building true drag-and-drop column remapping would mean re-engineering those adapters' matching contracts - a materially larger, higher-regression-risk change than this stage's budget allows, and not required to satisfy "mapping only when needed" (an unrecognized sheet is the one real case that needs a decision, and the correct, safe decision there is "fix the source file and re-upload," not "let the browser guess a mapping the server never validated"). The Mapping step is real (it shows exactly what was recognized/ignored and blocks progress on a real problem) but does not accept a redirected mapping.

**Error taxonomy** (`src/server/imports/error-taxonomy.ts`): FILE / STRUCTURE / ROW / AUTHORIZATION / SYSTEM, each with a `correctable` flag; used by the generic dispatch routes for `ImportAdapterError`, and by the client (`src/features/imports/api-client.ts`, `copy.ts`) to render a category-labeled banner instead of a generic failure. Every branch is a closed-list reason code with a hand-written safe message - nothing here ever formats a caught exception's own text.

**Hard limits** (`src/server/imports/file-safety.ts`, enforced in `src/server/analytics/xlsx-parser.ts`, shared by both adapters): `MAX_IMPORT_FILE_BYTES` 10 MB, `MAX_IMPORT_ROWS_PER_BATCH` 5000, `MAX_IMPORT_SHEETS_PER_FILE` 20 (all pre-existing, unchanged), plus new `MAX_IMPORT_CELL_CHARS` 20,000 and `MAX_IMPORT_DECOMPRESSED_CHARS` 25,000,000 (a running total of every character read out of every cell, across every sheet - the decompression-bomb defense; `parseWorkbookBuffer`'s new `includeBlankRows` option defaults to `false`, preserving the Analytics pipeline's existing blank-row-skip behavior exactly, and is opted into only by the generic preview module).

**Partial success / quarantine / resume** (Analytics): a per-row COMMIT failure (never a validation failure) is classified `quarantined` - a genuinely new, tenth `AnalyticsRowClassification` value (the spec's own explicit allowance for a state the original nine didn't cover). `resumeAnalyticsImportBatch` (new, `src/server/analytics/import-service.ts`) retries only quarantined rows, under the SAME `batchRef` (never a new batch), re-authorizes and re-validates via the exact same `runAnalyticsImportPipeline`/`commitContentRow`/`commitChannelRow` execute uses, requires the actor re-upload the exact same source file (sourceHash checked), and is resumable from either `COMPLETED_WITH_ERRORS` or `FAILED` (a batch where every row quarantined is `FAILED`, not `COMPLETED_WITH_ERRORS`, since zero rows succeeded - both are resumable as long as `quarantinedRows > 0`). `AnalyticsImportBatchDoc` gained `quarantinedRows`, `attempts`, `attemptHistory[]` (all `.default()`-backed, so every pre-existing batch doc still parses). Proven end-to-end against the real emulator with a test-only fault-injection seam (`setAnalyticsCommitFaultHookForTests`, same idiom as onboarding's own `setOnboardingFaultHookForTests`) - see `src/server/analytics/import-resume.emulator.test.ts`. contract-bundle's own "resume" is the existing per-row onboarding step-ledger (re-executing the same bundle resumes any row that didn't finish) - no second mechanism was added, by design (see adapter scope note above).

**Idempotency**: Analytics batch-level source-hash claim (pre-existing, unchanged, still proven) plus row-level identity-key dedup; contract-bundle row-level via the onboarding ledger's own `clientRequestId` fingerprint (deterministic per `sha256(sourceHash:sheetName:rowNumber)`), so re-running the exact same bundle file is a safe no-op replay, never a duplicate Partner/Vendor/Agreement.

Fields: `notificationRef`, `recipientUserRef`, `type` (closed 10-value enum), `sourceDomain`, `sourceRef`, `sourceEventKey` (operator-facing identity string, never shown to the client), `title`/`bodyPreview` (safe copy only, built exclusively by `copy.ts`'s templates), `deepLink` (app-relative path only, regex-enforced, never an absolute URL), `severity`, `dedupeKey`, `createdAt`/`createdByUserRef`, `readAt`/`dismissedAt`/`staleAt`/`expiresAt` (all nullable), and two server-only-derived denormalized booleans `unread`/`dismissed` that exist purely so the recipient+unread and recipient+dismissed list/count queries stay cheap equality-filter queries (spec section 9/13's "do not count by downloading all notification docs"). An append-only `notifications/{ref}/events` subcollection records NOTIFICATION_CREATED/READ/DISMISSED per notification, plus a top-level `notificationBulkEvents` collection for the one-row-per-call MARK_ALL_READ audit event - both built with the same explicit-metadata-allowlist idiom as `src/server/operations/task-events.ts` (title/bodyPreview are never allowlisted into an event's metadata - spec section 24's "avoid duplicating sensitive notification body"). Never written to `src/server/authz/audit.ts`'s `auditEvents` - that enum is Administration's own closed access-changing-operations trail, not a domain-agnostic log (a real repository fact found during reconnaissance, not assumed).

**Recipient isolation is authoritative** (`notifications-gate.ts`): deliberately NOT the standard FeatureAccess/ActionPermission/RecordScope chain every other domain uses - a user's own notification inbox is an inherently personal resource, always visible to any admitted/active actor regardless of feature grants, with no GLOBAL-scope-admin override of any kind (a judgment call, documented in the gate file's own header comment, precisely because forcing the general scope machinery on here would invite exactly the "admin sees everyone's notifications" mistake the spec's own section 3 warns against). Admission is `actor !== null` (resolveActor already only returns a non-null actor for an admitted/active user); every single query/mutation independently re-checks `recipientUserRef === actor.userRef`, never relaxed. A wrong-owner ref and a fully nonexistent ref both return the identical neutral 404 (`notificationsNotFoundResult()`) - never a distinct "forbidden" that would itself leak "this ref exists" to a guesser. `"notifications"` was added to the `FeatureId` union (`src/server/authz/features.ts`) for consistency/future Administration-tooling potential only - it gates nothing about a recipient's own inbox today.

**Event catalog - 10 supported types** (`src/server/notifications/projection.ts`, one function per type, each server-resolves its own recipient(s) and fails closed - never emits - when recipient context is insufficient):
1. **TASK_ASSIGNED** - `src/server/operations/task-service.ts`'s `createTask` (MANUAL origin only - see below), recipient = `assigneeUserRef`.
2. **TASK_REASSIGNED** - `task-lifecycle-service.ts`'s `reassignTask`, recipient = new `assigneeUserRef`; distinguisher = the head's new `docVersion` (so a later reassignment back to the same person still produces a fresh notification). Judgment call, documented in `projection.ts`: the PREVIOUS assignee does NOT get a second "unassigned" notification - the spec's own catalog only asks for the new assignee's attention, and there is no established safe-copy pattern anywhere in this codebase for a "no longer assigned" event.
3. **MEETING_CREATED** - `notes-meetings/meeting-service.ts`'s `createMeeting`, recipients = every participant excluding the organizer.
4. **MEETING_REVISED** - `reviseMeeting`, recipients = current participants excluding the actor, fired ONLY when the revision is judged "material" (title, scheduled time, or participant roster changed - a documented judgment call in the code; a pure agenda/summary/decisions text edit does not re-notify every participant, avoiding noisy duplicates for routine note-taking).
5. **ACTION_ITEM_ASSIGNED** - `action-item-service.ts`'s `createActionItem`, recipient = the assignee, only when one was supplied at creation.
6. **ACTION_ITEM_PROMOTED** - `notes-meetings/promotion.ts`'s `promoteActionItem`, recipient = the resulting Task's assignee. Double-notification risk resolved deliberately: `promoteActionItem` calls Operations' `generateSystemTask` (MODULE_ACTION origin), which the TASK_ASSIGNED hook (#1) is NOT wired into (that hook lives only on the MANUAL-origin `createTask` path) - so a promotion always fires exactly this one notification, never two. Fires only on the genuinely new link (not the idempotent "already promoted" fast path).
7. **CONTENT_REVIEW_DECISION** - `content-lifecycle-service.ts`'s `approveContentThread`/`requestContentRevision`, recipient = the owning Assignment's `ownerUid` (resolved to a `userRef`), skipped when null or when the recipient is the actor themselves. Framed as "a content review decision was made on an assignment you own" rather than the spec's literal "review requested/decision to the submitter" wording, because Content submission is external-partner/token-driven with no internal submitter to notify (a real repository fact, not a shortcut) - "review REQUESTED" is correspondingly out of scope (see below).
8. **REPORT_FINALIZED** - `report-lifecycle-service.ts`'s `finalizeReportVersion`, recipient = the finalized version's own `actorUserRef` (the drafter), skipped when `finalizedByUserRef === actorUserRef` (no attention value in your own just-completed action) and on an idempotent retry.
9. **REPORT_SUPERSEDED** - the SAME `finalizeReportVersion` call (finalize and supersede happen in one transaction), recipient = the previous finalized version's own `actorUserRef`, skipped when the superseding actor is the same person.
10. **ASSIGNMENT_CREATED** - `assignments/assignment-service.ts`'s `createAssignmentInternal`, recipient = the new Assignment's `ownerUid` (inherited from its Campaign, per that file's own existing comment - "Assignment has no separately-settable owner of its own"), skipped when null or self.

**5 intentionally unsupported event classes** (each a real, verified repository fact, not a time-budget shortcut - "fail closed / document, never guess a recipient" per spec section 6):
- **Task due-soon/overdue, MeetingActionItem due-soon, Reminder due** - no scheduled/cron infrastructure exists anywhere in this codebase (confirmed by repo-wide search); Reminders' own "DUE" state is computed purely on-read (`client-dto.ts`'s `if (head.status === "SCHEDULED" && head.reminderAt <= nowIso) return "DUE"`, no persisted transition ever fires) - there is no honest trigger point to hook a notification into without building fake polling infrastructure, explicitly out of this stage's scope.
- **Approval requested/assigned/resolved** - the Approval Queue (`operations/approval-queue/approval-queue-service.ts`) is an explicitly documented derived read model with NO persisted Firestore collection, computed fresh every call from 4 separate source modules (Partner Review, Payable, Invoice, Payment); none of those 4 has a clearly resolvable named approver in its own data today, and hooking all 4 would be a large, undirected expansion of this stage's scope.
- **Report submitted for review** - `reviewerUserRef` is a real schema field on `ReportVersionDoc` that is written `null` at every single write site in `report-lifecycle-service.ts` (confirmed - `submitReportForReview` never collects/resolves a reviewer); inventing a recipient or broadcasting to every finalize-capable role would violate spec section 6's own "never infer recipients from role rank / never broadcast" rule.
- **Content review REQUESTED** (as opposed to the review DECISION, which is supported - #7 above) - submission only happens via the public, unauthenticated, token-driven external-partner flow; there is no internal user to notify.
- **All Finance notifications** - no per-record recipient/approver/reviewer field exists anywhere in Finance's data model (Payables/Invoices/Payments move state via ActionPermission grants only, never a named assignee) - matches the spec's own explicitly anticipated "if safe recipient resolution is not explicit today, leave Finance notifications intentionally unsupported and document why" outcome exactly.

**Dedupe/idempotency** (`ids.ts` + `notification-service.ts`'s `createNotification`): `dedupeKey = sourceDomain|sourceRef|type|recipientUserRef|distinguisher` (distinguisher defaults to a constant for a one-shot event, or a real changing value - a `docVersion`, a version number - for a genuinely recurring one), `notificationRef = ntf_<sha256(dedupeKey)>`. Persistence uses the SAME race-safe "read inside a Firestore transaction, conditionally create" idiom as `operations/reminder-service.ts`'s `createReminder`/`task-service.ts`'s `generateSystemTask` (Firestore's own automatic transaction-conflict-and-retry is what makes concurrent emission safe, not an application lock) - proven directly against the real emulator (retry converges on the same ref; 3-way concurrent emission for the same event+recipient converges on exactly one doc; concurrent emission for two DIFFERENT recipients of the same event never cross-writes).

**Read/unread/dismiss/mark-all-read** (spec section 8): `markNotificationRead`/`dismissNotification` are idempotent (re-marking an already-read/dismissed notification is a no-op success, not an error) and independently re-verify `recipientUserRef` inside their own transaction. Dismiss also implies read (no meaningful "unread and dismissed" state) and hides the notification from the "unread"/"all" default view while preserving it under "dismissed" (never deleted). `markAllNotificationsRead` operates on the caller's own bounded page (`MARK_ALL_READ_BATCH_LIMIT = 200`, never an unbounded write) and writes one summary `NOTIFICATION_MARK_ALL_READ` audit row, not one per notification.

**Unread count** (spec section 9): `countUnreadNotifications` uses a real Firestore aggregation `.count().get()` query (`firebase-admin ^14.4.0` supports this) over `recipientUserRef == && unread == true` - a pure equality-only, no-orderBy query, so Firestore serves it from single-field indexes via zig-zag merge with no composite index needed and no document download.

**Query/storage design** (spec section 13, `firestore.indexes.json`): three composite indexes added - `(recipientUserRef, createdAt desc)` for "all"; `(recipientUserRef, unread, createdAt desc)` for "unread"; `(recipientUserRef, dismissed, createdAt desc)` for "dismissed". Bounded cursor pagination (`base64url(createdAt|notificationRef)`, `.startAfter()`), capped at `MAX_NOTIFICATION_LIST_SCAN = 100` server-side and `MAX_NOTIFICATION_PAGE_SIZE = 50` per page. Never a broad/unscoped collection query.

**Deep links + reauthorization** (spec section 10): every deep link is an app-relative path into a real, already-authorized single-item route (`deep-links.ts`) - Task → `/operations/tasks/{ref}`, Content → `/content/{ref}`, Assignment → `/assignments/{ref}`, Meeting/ActionItem → the owning record's own page (via the SAME `owner-registry.ts` mapping Notes/Meetings' own UI already uses - Notes/Meetings has no dedicated Meeting/ActionItem route or query-param convention of its own, a real, disclosed limitation, not fabricated), Report → `/reports/{reportId}` (the catalog page only - `ReportRunner.tsx` has no query-param handling to pre-select a specific run/version; adding that was judged out of this stage's time budget, disclosed rather than silently accepted). Clicking a notification never grants source access on its own - the destination route independently re-runs `getTask`/`getContent`/etc.'s own authorization from scratch. Proven end-to-end against the real emulator+browser: a Task reassigned away from its original recipient (with no region/team scope of its own) renders the SAME neutral "Task not found" state Operations already uses for any denied/out-of-scope task, never a broken page or a content leak.

**Safe copy / sensitive-access behavior** (spec section 11/12): every title/body string is built exclusively by `copy.ts`'s small templates from an already-safe display value (a task/meeting title, an action-item text) the owning module's own DTO layer already treats as safe for the people who can see the record - never a raw ref/uid/object path/storage ref/raw Firebase error/KYC/bank/tax value/full Note or Meeting text. ## OCR Completion (this stage)

Accepted local SHA: see `git log` on branch `ocr-completion` (commits start `OCR Completion`), based on `main @ a67f43a`.

**Mission**: add a real, local, offline OCR fallback for scanned/image-only Agreement and Invoice PDFs, server-side, no external OCR provider, feeding the SAME existing domain parsers native text already feeds - never a parallel Agreement/Invoice truth.

**Engine selected**: `tesseract.js` (pure JS/WASM Tesseract, npm `tesseract.js@7.0.0`) for recognition + `unpdf`'s own `renderPageAsImage` (backed by `@napi-rs/canvas@0.1.100`) for PDF page rasterization - both new dependencies, both install with zero native-compilation steps (prebuilt per-platform binaries / pure WASM), both run in-process with no shell exec, no external executable, no arbitrary file paths passed to a subprocess. The committed English trained-data language file (`src/server/finance-shared/ocr-assets/eng.traineddata.gz`, 2,947,315 bytes, gzip, server-only, never under `public/`) is passed as an explicit local `langPath`/`cachePath` (`cacheMethod: "none"`, so nothing is ever written to a filesystem cache) on every `createWorker()` call - verified directly against `tesseract.js`'s own source that a non-URL `langPath` takes the local-filesystem-read branch exclusively, and proven empirically: a dedicated test patches `globalThis.fetch` to throw and real end-to-end OCR still succeeds (`extraction/ocr-provider.test.ts`, both modules).

**Architecture**: `validate -> extract native PDF text -> if usable, existing flow -> if native text is insufficient (`no_extractable_text` only - never on encrypted/too-many-pages/timeout/malformed), invoke OCR -> feed OCR page text into the EXISTING `extractAgreementFields`/`extractInvoiceFields` rule engines, completely unmodified`. Two deliberate LOCAL COPIES of the OCR provider (`finance-agreements/extraction/ocr-provider.ts`, `finance-invoices/extraction/ocr-provider.ts`), matching this codebase's own established "small local copy of generic pure logic per feature module rather than a cross-module import" convention (the same discipline `pdf-text.ts` already uses between the two modules) - both reference the SAME committed language asset by filesystem path (not a module import), so it is committed exactly once. `finance-agreements-static.test.ts`'s `extraction/` import allowlist was deliberately widened for exactly `tesseract.js`/`@napi-rs/canvas` (the one static guard the reconnaissance addendum flagged as needing a reviewed edit); Invoices has no equivalent per-folder guard (confirmed by reading `finance-invoices-static.test.ts` in full), so no edit was needed there. `payee-identity/`'s own explicit "no OCR reference" static guard was left completely untouched - no OCR code was added anywhere under that folder (see the disclosed gap below).

**Provenance/confidence** (`ExtractionSource`/`InvoiceExtractionSource`, new, additive fields on `extractionRunDocSchema` and the Invoice extraction-preview DTO): `native` vs `ocr`, provider id/version, per-page confidence BAND only (`USABLE`/`LOW`/`FAILED` - never a raw percentage in the DTO, per spec section 9). Confidence bands: `>=75` USABLE, `40-75` LOW (field-level confidence capped at LOW, routed to human review), `<40` FAILED (that page's text is discarded before field extraction runs, so a garbled scan can never fabricate a plausible-looking low-confidence proposal). These thresholds are grounded in a real, hands-on feasibility spike performed before this stage began (a clean synthetic fixture scored 93-95% mean confidence with perfect recovery; a deliberately speckle-noised fixture scored ~20% and was genuinely garbled) - re-confirmed with this stage's own real fixtures. OCR-sourced field confidence is NEVER `HIGH`, whatever the underlying OCR engine confidence (spec section 9 - OCR evidence is categorically lower trust than a clean native PDF text layer) - enforced in code and asserted directly against a real end-to-end OCR run in the emulator tests.

**Idempotency** (spec section 15): `ocr_` + `sha256(artifactSha256|providerId|providerVersion|configVersion)`, the SAME claim idiom Agreements' own `contractArtifactClaimId` already established (a full-hex-digest claim, distinct from Reports/Notifications' own `.create()`-based idiom) - a config/engine upgrade or a genuinely different document always gets a fresh claim, never stale output. The recovered OCR page TEXT (never a field value, never image bytes) is cached server-side, keyed by that claim id: `financeAgreementOcrRuns` / `financeInvoiceOcrRuns` (new collections, never exposed by an ordinary DTO, read-gated exactly like the existing restricted-extraction record). **Disclosed, deliberate design choice**: the cache lookup/write is non-transactional (a benign race between two concurrent first-time OCR requests for the same document may run Tesseract twice; both converge on the same deterministic claim id and equivalent content - never a correctness issue, only a possible redundant computation on the very first concurrent request). Correctness against a STALE OCR result racing a newer document version is enforced by the PRE-EXISTING mechanism this stage relied on rather than duplicated: only the currently-open Agreement version's own extraction-run transaction can record a run (`extraction-service.ts`'s existing `head.openVersion !== version.version` check) - no new dedicated stale-result-rejection test was written this stage beyond what that existing mechanism already covers structurally.

**Invoice-specific decision** (flagged explicitly by the reconnaissance addendum as needing a real, disclosed decision, not a silent pick): Invoice extraction is EPHEMERAL/read-only by architecture (`extraction-preview-service.ts`'s own header - nothing persists an extraction run). OCR is comparatively expensive, so - and ONLY so - the recovered OCR page TEXT is cached (`financeInvoiceOcrRuns`, above); field extraction FROM that cached text stays exactly as ephemeral and recomputed-on-each-call as it is today.

**Resource limits** (spec section 17): `MAX_OCR_PAGES` 15 (Agreements) / 10 (Invoices, both well below the existing cheap-native-parse caps of 60/20); rasterization scale 2.0x (~144 effective DPI, the addendum's own measured sweet spot); `MAX_RASTER_PIXELS` 25,000,000 per page, checked BEFORE the memory-heavy render call (a pathological PDF declaring an enormous page size is refused up front - verified with an adversarial 20,000x20,000pt fixture); per-page timeout 25s + whole-document timeout 180s (both real, injectable, and tested by forcing a real timeout against a real OCR call, not simulated). A single bad page (corrupt rasterization, a per-page timeout) is recorded as `FAILED` and does not sink the rest of the document.

**File safety / security** (spec section 18/37): OCR only ever runs on bytes that already passed the existing PDF validation (magic-byte check, size cap, `sha256` artifact-integrity check) - no new file-type surface. No temp files anywhere (matches this codebase's existing convention - `renderPageAsImage` returns an in-memory buffer, `tesseract.js`'s `recognize()` accepts it directly). OCR text is treated as untrusted input exactly like native-extracted text already is (never rendered as HTML, flows through the exact same restricted/ordinary split the moment field extraction runs on it).

**Real fixtures** (spec section 26, `src/server/finance-shared/ocr-testing/build-scanned-pdf.ts` + each module's own `testing/ocr-fixtures.ts`): genuine image-only PDFs built by rendering text onto an in-memory `@napi-rs/canvas` canvas, exporting to PNG, and embedding that PNG as a full-page image in a fresh `pdf-lib` PDF - NO PDF text operators anywhere. Each fixture's image-only-ness is directly proven (native `extractPdfText` recovers zero usable text before the OCR test trusts it). A degraded/low-confidence variant (12% random speckle noise) proves a bad scan correctly routes to manual review rather than fabricating a clean result.

**Production build / deployment finding** (spec section 34 - a real, load-bearing finding, not a hypothetical risk): `next build` FAILED before a fix - Turbopack cannot bundle `@napi-rs/canvas`'s native `.node` binding loader into a Server Component/API-route chunk ("non-ecmascript placeable asset"). Fixed with `serverExternalPackages: ["@napi-rs/canvas", "tesseract.js", "tesseract.js-core"]` in `next.config.ts` (tells Next to leave these as real Node `require()` calls at runtime rather than bundling them). Verified further with a real `next build` followed by a real `next start` on a private port: both OCR-touching API routes (`POST /api/finance/contracts/extract`, `POST /api/finance/invoices/[invoiceRef]/extraction`) load and execute cleanly under the compiled production server (a real 401 Forbidden for an unauthenticated request, never a 500 native-module-resolution crash) - this is genuine evidence the fix works at actual runtime, not just at build time.
