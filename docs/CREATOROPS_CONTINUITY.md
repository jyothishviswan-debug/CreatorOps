**Scope decision - Mapping is informational, not a free-form remapper**: the existing Analytics adapters recognize a sheet by matching a FIXED set of header aliases per platform template (all-or-nothing per sheet), not by letting an actor redirect an arbitrary column to an arbitrary canonical field. Building true drag-and-drop column remapping would mean re-engineering those adapters' matching contracts - a materially larger, higher-regression-risk change than this stage's budget allows, and not required to satisfy "mapping only when needed" (an unrecognized sheet is the one real case that needs a decision, and the correct, safe decision there is "fix the source file and re-upload," not "let the browser guess a mapping the server never validated"). The Mapping step is real (it shows exactly what was recognized/ignored and blocks progress on a real problem) but does not accept a redirected mapping.

**Error taxonomy** (`src/server/imports/error-taxonomy.ts`): FILE / STRUCTURE / ROW / AUTHORIZATION / SYSTEM, each with a `correctable` flag; used by the generic dispatch routes for `ImportAdapterError`, and by the client (`src/features/imports/api-client.ts`, `copy.ts`) to render a category-labeled banner instead of a generic failure. Every branch is a closed-list reason code with a hand-written safe message - nothing here ever formats a caught exception's own text.

**Hard limits** (`src/server/imports/file-safety.ts`, enforced in `src/server/analytics/xlsx-parser.ts`, shared by both adapters): `MAX_IMPORT_FILE_BYTES` 10 MB, `MAX_IMPORT_ROWS_PER_BATCH` 5000, `MAX_IMPORT_SHEETS_PER_FILE` 20 (all pre-existing, unchanged), plus new `MAX_IMPORT_CELL_CHARS` 20,000 and `MAX_IMPORT_DECOMPRESSED_CHARS` 25,000,000 (a running total of every character read out of every cell, across every sheet - the decompression-bomb defense; `parseWorkbookBuffer`'s new `includeBlankRows` option defaults to `false`, preserving the Analytics pipeline's existing blank-row-skip behavior exactly, and is opted into only by the generic preview module).

**Idempotency**: Analytics batch-level source-hash claim (pre-existing, unchanged, still proven) plus row-level identity-key dedup; contract-bundle row-level via the onboarding ledger's own `clientRequestId` fingerprint (deterministic per `sha256(sourceHash:sheetName:rowNumber)`), so re-running the exact same bundle file is a safe no-op replay, never a duplicate Partner/Vendor/Agreement.

**Reminder-link (section 10) - deliberately deferred, not built**: Operations' Reminder head requires a mandatory `target: TargetReference` from the SAME closed enum a Task uses; there is no `MEETING_ACTION_ITEM` case and adding one would blur Reminder's own target semantics for a feature the spec explicitly allows deferring. `linkedReminderRef` is reserved (always null) on the schema so a later stage can wire it without a migration.

**Authorization** (`notes-meetings-gate.ts`): `Authentication -> Admission -> FeatureAccess -> ActionPermission -> RecordScope -> SensitiveAccess`, explicit grants only (no role rank, proven by static guard). Deliberately NO new top-level `notes`/`meetings` FeatureId - three new ActionIds (`manage_notes`, `manage_meetings`, `promote_action_item`) were added to each of the six SUPPORTED owner types' own existing feature (`discovery`/`partners`/`vendors`/`campaigns`/`assignments`/`content`), so "can this actor manage Notes/Meetings on this Partner" composes that Partner's own FeatureAccess with the SAME live RecordScope check opening the Partner itself already uses - never a second, parallel scope model. `partnership_manager`/`partnership_head` both hold all three actions on all six owner features (no Manager-vs-Head split, mirroring Operations' own `manage_tasks` shape - "no separate approval step" reasoning applies identically here). A new sensitive-access category, `notes_meetings_sensitive`, gates a RESTRICTED Note/Meeting's own body/summary/decisions/attachments - Head + Super Admin only, Manager holds the ACTION (can author/mark-restricted) without the CATEGORY (cannot read one back), the same non-monotonic action-vs-category independence every other sensitive category in this codebase already proves.

**Visibility/sensitivity**: a RESTRICTED Note/Meeting's existence, author, time, title and status are always visible; body/summary/decisions/participants/attachments are redacted (`redacted: true`, fields `null`) for an actor lacking the category - never hidden entirely, and identically redacted across the CURRENT content and every past VERSION (visibility is not itself revisable this stage - set once at creation).

**Attachments** (`attachment-store.ts`, structural sibling of `exports/artifact-store.ts` - chosen over Finance Agreement's fuller Drive-adapter-chooser split, since Notes/Meetings never wires real Drive at all): Storage-emulator-backed in production/dev, in-memory fake in unit tests; opaque `att_<hex20>` client ref, server-only Storage locator never in any DTO/event/log; bytes delivered only through a re-authorized, sensitivity-checked download route. Capped 10 MB, allowlisted mime types, capped 20 per Note/Meeting (enforced both optimistically and, correctly, inside the same transaction that appends the ref - a genuine bug the static "bounded queries" guard caught during this stage was fixed: the attachment list query gained an explicit `.limit()`, and the parent-doc write moved from an ad-hoc `tx.update` in the service file into `firestore.ts`'s own `txAppendAttachmentToParent`, so every write in this module funnels through one place, matching every other module's own discipline).

**Audit/events** (`notes-meetings-events.ts` + `types.ts`'s schema, mirroring `task-events.ts` exactly, including its own duplicated `IDENTITY_SHAPED` PII-scrubbing regex bank): a per-module append-only event trail (never the global Administration `auditEvents` collection) with a hard per-key metadata allowlist - the event never carries `body`/`summary`/`decisions`/`agenda` at all, only structural facts (refs, counts, booleans, a scrubbed short reason). Domain events are real (`NOTE_CREATED/REVISED/ARCHIVED`, `MEETING_CREATED/REVISED/CANCELLED`, `ACTION_ITEM_CREATED/REVISED/COMPLETED/CANCELLED/PROMOTED`, plus `*_ATTACHMENT_ADDED`) so the later Notifications stage can subscribe directly - no fake notification record, no email/SMS/Slack provider, per section 20's explicit prohibition (proven by static guard).

**A real, reproducible race-condition bug found and fixed during Playwright verification** (not a test artifact - confirmed via a direct server round trip that CREATE always succeeded and persisted; only the client's own list state was wrong, and it reproduced identically under `next dev` and a production `next build`/`next start`): `NoteThread`/`MeetingThread`/`MeetingDetailDialog` each had a mount-time fetch and one or more separate post-mutation `refresh()` calls as two independent, unordered network round trips; under real latency the slower, earlier-started mount fetch could resolve AFTER the faster, later-started refresh and silently overwrite the just-created data with the stale pre-mutation list - a real bug any user clicking "Save" quickly after the page loads could hit, not specific to automation. Fixed with a small `useLatestRequest()` hook (`use-latest-request.ts`): every fetch is tagged with a monotonically increasing id at issue time, and a response is only applied if it is still the most recently issued fetch when it arrives.

**UI** (`src/features/notes-meetings/`): one reusable `NotesMeetingsSection` (Notes/Meetings sub-tabs via the shared `LocalTabs` primitive) embedded two ways - as a dialog (`NotesMeetingsDialog`, replacing the two placeholder dialogs at Assignment/Content's own frozen golden-master "Notes & meetings" tab-strip slot, including a real compact preview card in the third-grid tile that used to say "Not yet built") and as a local tab/section (added to Partner/Vendor/Campaign's own existing tab-strip pattern; Discovery Lead gets a persistent contextual section below its lifecycle-stage strip instead of a new tab, since that strip IS the Discovery lifecycle itself, not a generic tab set - a deliberate surface choice per owner page's own existing structure, never a new design system). Meeting detail is a dialog with Detail/History tabs, participants/decisions/summary, revise, cancel, attachments, and a compact action-item panel (add/complete/cancel/promote, with an inline assignee picker only shown when the item has none). No raw `note_`/`mtg_`/`mai_`/`att_` ref is ever a primary UI label - proven by a Playwright assertion scanning the full rendered body/dialog text.

## Closed architecture decisions
- Authorization is explicit grants only (FeatureAccess, ActionPermission, RecordScope, SensitiveAccess, LifecyclePreconditions); no role ranking, wildcard or minimumRole.
- Operations never owns source lifecycle; Approval Queue is a derived read model; Reports never mutate sources; Export re-authorizes against source scope.
- Partner Review keeps Production / Compliance / Performance separate; no synthetic score; missing evidence is never zero.
- Overview (`src/app/dashboard/page.tsx`, `src/ui/Overview.tsx`, `src/ui/overview.css`) is frozen.
