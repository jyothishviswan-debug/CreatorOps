**Scope decision - Mapping is informational, not a free-form remapper**: the existing Analytics adapters recognize a sheet by matching a FIXED set of header aliases per platform template (all-or-nothing per sheet), not by letting an actor redirect an arbitrary column to an arbitrary canonical field. Building true drag-and-drop column remapping would mean re-engineering those adapters' matching contracts - a materially larger, higher-regression-risk change than this stage's budget allows, and not required to satisfy "mapping only when needed" (an unrecognized sheet is the one real case that needs a decision, and the correct, safe decision there is "fix the source file and re-upload," not "let the browser guess a mapping the server never validated"). The Mapping step is real (it shows exactly what was recognized/ignored and blocks progress on a real problem) but does not accept a redirected mapping.

**Error taxonomy** (`src/server/imports/error-taxonomy.ts`): FILE / STRUCTURE / ROW / AUTHORIZATION / SYSTEM, each with a `correctable` flag; used by the generic dispatch routes for `ImportAdapterError`, and by the client (`src/features/imports/api-client.ts`, `copy.ts`) to render a category-labeled banner instead of a generic failure. Every branch is a closed-list reason code with a hand-written safe message - nothing here ever formats a caught exception's own text.

**Hard limits** (`src/server/imports/file-safety.ts`, enforced in `src/server/analytics/xlsx-parser.ts`, shared by both adapters): `MAX_IMPORT_FILE_BYTES` 10 MB, `MAX_IMPORT_ROWS_PER_BATCH` 5000, `MAX_IMPORT_SHEETS_PER_FILE` 20 (all pre-existing, unchanged), plus new `MAX_IMPORT_CELL_CHARS` 20,000 and `MAX_IMPORT_DECOMPRESSED_CHARS` 25,000,000 (a running total of every character read out of every cell, across every sheet - the decompression-bomb defense; `parseWorkbookBuffer`'s new `includeBlankRows` option defaults to `false`, preserving the Analytics pipeline's existing blank-row-skip behavior exactly, and is opted into only by the generic preview module).

**Partial success / quarantine / resume** (Analytics): a per-row COMMIT failure (never a validation failure) is classified `quarantined` - a genuinely new, tenth `AnalyticsRowClassification` value (the spec's own explicit allowance for a state the original nine didn't cover). `resumeAnalyticsImportBatch` (new, `src/server/analytics/import-service.ts`) retries only quarantined rows, under the SAME `batchRef` (never a new batch), re-authorizes and re-validates via the exact same `runAnalyticsImportPipeline`/`commitContentRow`/`commitChannelRow` execute uses, requires the actor re-upload the exact same source file (sourceHash checked), and is resumable from either `COMPLETED_WITH_ERRORS` or `FAILED` (a batch where every row quarantined is `FAILED`, not `COMPLETED_WITH_ERRORS`, since zero rows succeeded - both are resumable as long as `quarantinedRows > 0`). `AnalyticsImportBatchDoc` gained `quarantinedRows`, `attempts`, `attemptHistory[]` (all `.default()`-backed, so every pre-existing batch doc still parses). Proven end-to-end against the real emulator with a test-only fault-injection seam (`setAnalyticsCommitFaultHookForTests`, same idiom as onboarding's own `setOnboardingFaultHookForTests`) - see `src/server/analytics/import-resume.emulator.test.ts`. contract-bundle's own "resume" is the existing per-row onboarding step-ledger (re-executing the same bundle resumes any row that didn't finish) - no second mechanism was added, by design (see adapter scope note above).

**Idempotency**: Analytics batch-level source-hash claim (pre-existing, unchanged, still proven) plus row-level identity-key dedup; contract-bundle row-level via the onboarding ledger's own `clientRequestId` fingerprint (deterministic per `sha256(sourceHash:sheetName:rowNumber)`), so re-running the exact same bundle file is a safe no-op replay, never a duplicate Partner/Vendor/Agreement.

## Recipient-Scoped Notifications Completion (this stage)

Accepted local SHA: see `git log` on branch `notifications-completion` (first commit message starts `Notifications Completion`), based on local `main @ f2c394c`.

**Mission**: build the missing recipient-scoped in-app Notifications subsystem as a real trusted feature - recipient attention state, derived from authoritative source-domain events, deduplicated, scoped to exactly one recipient, read/dismiss state, deep-linkable, reauthorized at open/click time, never the source of truth for the underlying business event. Not email/SMS/WhatsApp/Slack/push/Tasks/Approvals/Reminders/Audit Log.

**Data model** (`src/server/notifications/types.ts`, `notificationDocSchema`): one doc per (recipient, event) at collection `notifications`, id = `ntf_<sha256(dedupeKey)>` (deterministic, mirrors `src/server/reports/ids.ts`'s `generateArtifactRef` idiom exactly). Fields: `notificationRef`, `recipientUserRef`, `type` (closed 10-value enum), `sourceDomain`, `sourceRef`, `sourceEventKey` (operator-facing identity string, never shown to the client), `title`/`bodyPreview` (safe copy only, built exclusively by `copy.ts`'s templates), `deepLink` (app-relative path only, regex-enforced, never an absolute URL), `severity`, `dedupeKey`, `createdAt`/`createdByUserRef`, `readAt`/`dismissedAt`/`staleAt`/`expiresAt` (all nullable), and two server-only-derived denormalized booleans `unread`/`dismissed` that exist purely so the recipient+unread and recipient+dismissed list/count queries stay cheap equality-filter queries (spec section 9/13's "do not count by downloading all notification docs"). An append-only `notifications/{ref}/events` subcollection records NOTIFICATION_CREATED/READ/DISMISSED per notification, plus a top-level `notificationBulkEvents` collection for the one-row-per-call MARK_ALL_READ audit event - both built with the same explicit-metadata-allowlist idiom as `src/server/operations/task-events.ts` (title/bodyPreview are never allowlisted into an event's metadata - spec section 24's "avoid duplicating sensitive notification body"). Never written to `src/server/authz/audit.ts`'s `auditEvents` - that enum is Administration's own closed access-changing-operations trail, not a domain-agnostic log (a real repository fact found during reconnaissance, not assumed).

**Recipient isolation is authoritative** (`notifications-gate.ts`): deliberately NOT the standard FeatureAccess/ActionPermission/RecordScope chain every other domain uses - a user's own notification inbox is an inherently personal resource, always visible to any admitted/active actor regardless of feature grants, with no GLOBAL-scope-admin override of any kind (a judgment call, documented in the gate file's own header comment, precisely because forcing the general scope machinery on here would invite exactly the "admin sees everyone's notifications" mistake the spec's own section 3 warns against). Admission is `actor !== null` (resolveActor already only returns a non-null actor for an admitted/active user); every single query/mutation independently re-checks `recipientUserRef === actor.userRef`, never relaxed. A wrong-owner ref and a fully nonexistent ref both return the identical neutral 404 (`notificationsNotFoundResult()`) - never a distinct "forbidden" that would itself leak "this ref exists" to a guesser. `"notifications"` was added to the `FeatureId` union (`src/server/authz/features.ts`) for consistency/future Administration-tooling potential only - it gates nothing about a recipient's own inbox today.

**Event catalog - 10 supported types** (`src/server/notifications/projection.ts`, one function per type, each server-resolves its own recipient(s) and fails closed - never emits - when recipient context is insufficient):
1. **TASK_ASSIGNED** - `src/server/operations/task-service.ts`'s `createTask` (MANUAL origin only - see below), recipient = `assigneeUserRef`.
2. **TASK_REASSIGNED** - `task-lifecycle-service.ts`'s `reassignTask`, recipient = new `assigneeUserRef`; distinguisher = the head's new `docVersion` (so a later reassignment back to the same person still produces a fresh notification). Judgment call, documented in `projection.ts`: the PREVIOUS assignee does NOT get a second "unassigned" notification - the spec's own catalog only asks for the new assignee's attention, and there is no established safe-copy pattern anywhere in this codebase for a "no longer assigned" event.
3. **MEETING_CREATED** - `notes-meetings/meeting-service.ts`'s `createMeeting`, recipients = every participant excluding the organizer.
4. **MEETING_REVISED** - `reviseMeeting`, recipients = current participants excluding the actor, fired ONLY when the revision is judged "material" (title, scheduled time, or participant roster changed - a documented judgment call in the code; a pure agenda/summary/decisions text edit does not re-notify every participant, avoiding noisy duplicates for routine note-taking).
5. **ACTION_ITEM_ASSIGNED** - `action-item-service.ts`'s `createActionItem`, recipient = the assignee, only when one was supplied at creation.
6. **ACTION_ITEM_PROMOTED** - `notes-meetings/promotion.ts`'s `promoteActionItem`, recipient = the resulting Task's assignee. Double-notification risk resolved deliberately: `promoteActionItem` calls Operations' `generateSystemTask` (MODULE_ACTION origin), which the TASK_ASSIGNED hook (#1) is NOT wired into (that hook lives only on the MANUAL-origin `createTask` path) - so a promotion always fires exactly this one notification, never two. Fires only on the genuinely new link (not the idempotent "already promoted" fast path).
7. **CONTENT_REVIEW_DECISION** - `content-lifecycle-service.ts`'s `approveContentThread`/`requestContentRevision`, recipient = the owning Assignment's `ownerUid` (resolved to a `userRef`), skipped when null or when the recipient is the actor themselves. Framed as "a content review decision was made on an assignment you own" rather than the spec's literal "review requested/decision to the submitter" wording, because Content submission is external-partner/token-driven with no internal submitter to notify (a real repository fact, not a shortcut) - "review REQUESTED" is correspondingly out of scope (see below).
8. **REPORT_FINALIZED** - `report-lifecycle-service.ts`'s `finalizeReportVersion`, recipient = the finalized version's own `actorUserRef` (the drafter), skipped when `finalizedByUserRef === actorUserRef` (no attention value in your own just-completed action) and on an idempotent retry.
9. **REPORT_SUPERSEDED** - the SAME `finalizeReportVersion` call (finalize and supersede happen in one transaction), recipient = the previous finalized version's own `actorUserRef`, skipped when the superseding actor is the same person.
10. **ASSIGNMENT_CREATED** - `assignments/assignment-service.ts`'s `createAssignmentInternal`, recipient = the new Assignment's `ownerUid` (inherited from its Campaign, per that file's own existing comment - "Assignment has no separately-settable owner of its own"), skipped when null or self.

**5 intentionally unsupported event classes** (each a real, verified repository fact, not a time-budget shortcut - "fail closed / document, never guess a recipient" per spec section 6):

- **Approval requested/assigned/resolved** - the Approval Queue (`operations/approval-queue/approval-queue-service.ts`) is an explicitly documented derived read model with NO persisted Firestore collection, computed fresh every call from 4 separate source modules (Partner Review, Payable, Invoice, Payment); none of those 4 has a clearly resolvable named approver in its own data today, and hooking all 4 would be a large, undirected expansion of this stage's scope.
- **Report submitted for review** - `reviewerUserRef` is a real schema field on `ReportVersionDoc` that is written `null` at every single write site in `report-lifecycle-service.ts` (confirmed - `submitReportForReview` never collects/resolves a reviewer); inventing a recipient or broadcasting to every finalize-capable role would violate spec section 6's own "never infer recipients from role rank / never broadcast" rule.

- **All Finance notifications** - no per-record recipient/approver/reviewer field exists anywhere in Finance's data model (Payables/Invoices/Payments move state via ActionPermission grants only, never a named assignee) - matches the spec's own explicitly anticipated "if safe recipient resolution is not explicit today, leave Finance notifications intentionally unsupported and document why" outcome exactly.

**Dedupe/idempotency** (`ids.ts` + `notification-service.ts`'s `createNotification`): `dedupeKey = sourceDomain|sourceRef|type|recipientUserRef|distinguisher` (distinguisher defaults to a constant for a one-shot event, or a real changing value - a `docVersion`, a version number - for a genuinely recurring one), `notificationRef = ntf_<sha256(dedupeKey)>`. Persistence uses the SAME race-safe "read inside a Firestore transaction, conditionally create" idiom as `operations/reminder-service.ts`'s `createReminder`/`task-service.ts`'s `generateSystemTask` (Firestore's own automatic transaction-conflict-and-retry is what makes concurrent emission safe, not an application lock) - proven directly against the real emulator (retry converges on the same ref; 3-way concurrent emission for the same event+recipient converges on exactly one doc; concurrent emission for two DIFFERENT recipients of the same event never cross-writes).

**Read/unread/dismiss/mark-all-read** (spec section 8): `markNotificationRead`/`dismissNotification` are idempotent (re-marking an already-read/dismissed notification is a no-op success, not an error) and independently re-verify `recipientUserRef` inside their own transaction. Dismiss also implies read (no meaningful "unread and dismissed" state) and hides the notification from the "unread"/"all" default view while preserving it under "dismissed" (never deleted). `markAllNotificationsRead` operates on the caller's own bounded page (`MARK_ALL_READ_BATCH_LIMIT = 200`, never an unbounded write) and writes one summary `NOTIFICATION_MARK_ALL_READ` audit row, not one per notification.

**Unread count** (spec section 9): `countUnreadNotifications` uses a real Firestore aggregation `.count().get()` query (`firebase-admin ^14.4.0` supports this) over `recipientUserRef == && unread == true` - a pure equality-only, no-orderBy query, so Firestore serves it from single-field indexes via zig-zag merge with no composite index needed and no document download.

**Query/storage design** (spec section 13, `firestore.indexes.json`): three composite indexes added - `(recipientUserRef, createdAt desc)` for "all"; `(recipientUserRef, unread, createdAt desc)` for "unread"; `(recipientUserRef, dismissed, createdAt desc)` for "dismissed". Bounded cursor pagination (`base64url(createdAt|notificationRef)`, `.startAfter()`), capped at `MAX_NOTIFICATION_LIST_SCAN = 100` server-side and `MAX_NOTIFICATION_PAGE_SIZE = 50` per page. Never a broad/unscoped collection query.

**Deep links + reauthorization** (spec section 10): every deep link is an app-relative path into a real, already-authorized single-item route (`deep-links.ts`) - Task → `/operations/tasks/{ref}`, Content → `/content/{ref}`, Assignment → `/assignments/{ref}`, Meeting/ActionItem → the owning record's own page (via the SAME `owner-registry.ts` mapping Notes/Meetings' own UI already uses - Notes/Meetings has no dedicated Meeting/ActionItem route or query-param convention of its own, a real, disclosed limitation, not fabricated), Report → `/reports/{reportId}` (the catalog page only - `ReportRunner.tsx` has no query-param handling to pre-select a specific run/version; adding that was judged out of this stage's time budget, disclosed rather than silently accepted). Clicking a notification never grants source access on its own - the destination route independently re-runs `getTask`/`getContent`/etc.'s own authorization from scratch. Proven end-to-end against the real emulator+browser: a Task reassigned away from its original recipient (with no region/team scope of its own) renders the SAME neutral "Task not found" state Operations already uses for any denied/out-of-scope task, never a broken page or a content leak.

**Safe copy / sensitive-access behavior** (spec section 11/12): every title/body string is built exclusively by `copy.ts`'s small templates from an already-safe display value (a task/meeting title, an action-item text) the owning module's own DTO layer already treats as safe for the people who can see the record - never a raw ref/uid/object path/storage ref/raw Firebase error/KYC/bank/tax value/full Note or Meeting text. Verified directly (unit tests assert no ref-shaped id appears in any built copy string; the emulator/Playwright suites assert the real opaque `taskRef` never appears in the panel's own rendered text).

**Topbar bell + panel** (`src/features/notifications/NotificationBell.tsx`, wired into `src/ui/Topbar.tsx` in place of the prior honestly-disabled bell): real unread badge (server-trusted count, capped display "9+"), anchored popover on desktop/tablet, promoted to a full-height drawer on mobile (`<=760px`, CSS-only via `foundation.css`'s own breakpoint convention) - a deliberate, disclosed departure from the golden master's own illustrative MODAL markup, matching the spec's own "panel/drawer" language instead. The panel is rendered through a React portal into `document.body`: the topbar's own `backdrop-filter` (pre-existing CSS) establishes a containing block for any `position:fixed` descendant, which would otherwise have confined the mobile drawer to the topbar's own 58px-tall box instead of the viewport - a real bug found and fixed via live-browser verification, not a hypothetical. Keyboard: Escape closes the panel and returns focus to the trigger button; initial focus moves into the panel on open (neither `MultiSelectDropdown`'s outside-click precedent nor `DialogShell`'s modal focus trap covered both on their own - added explicitly). Unread state is never color-only (a literal "· Unread" text suffix accompanies the dot indicator). Real-time behavior (spec section 16): refetch-on-mount/focus/visibilitychange + local optimistic mutation updates after read/dismiss/mark-all-read - NOT a Firestore listener (this codebase's `firestore.rules` is a blanket `allow read, write: if false`, and zero client-side Firestore listeners exist anywhere in the product; every screen already fetches through a trusted API route, so the bell does the same) and NOT a polling interval (no other component in this codebase polls on a timer). No dedicated `/notifications` page was built this stage - a deliberate "quick topbar panel only" scope decision (spec section 15's own explicit allowance), since the topbar panel already supports unread/all/dismissed filtering with cursor pagination server-side.

**API routes** (`src/app/api/notifications/*`): `GET /` (list, `status=unread|all|dismissed`, cursor), `GET /unread-count`, `POST /mark-all-read`, `POST /[notificationRef]/read`, `POST /[notificationRef]/dismiss` - all resolve the actor server-side via the same `resolveRequestActor` every other domain's `http.ts` re-exports, never trusting anything the client asserts about identity.
