## 2. Ground rules that governed this whole pilot

These were established and reinforced repeatedly, and apply to everything below:

1. **Never fabricate data.** Every number, date, KYC/PAN/Aadhaar/bank value, Analytics figure, or content link used in this pilot is real, supplied or confirmed by the user, or read directly from a real source (a real CSV export, a real signed Agreement). Whenever real data was missing, the correct move was always to pause and ask — never invent a plausible-looking substitute.
2. **Never make code changes without explicit authorization.** This was corrected sharply once this session ("who said to change code?") and has held since — code is only touched after a clear go-ahead for that specific change.
3. **Every fix must be real and root-cause, never a workaround.** Documented verbatim at the top of the findings doc: an entry is only marked **[FIXED]** once the underlying cause was actually addressed, with real verification (typecheck, lint, tests, live re-check) — not once a single symptom was patched around.
4. **No UI changes without explicit permission first**, and no substituting a different real metric into an already-approved UI slot without asking.

## 5. The Step 14D fix (finding #64) — full technical detail

### The problem
`policy-adapter.ts`'s `coversMonth` rule required an Agreement version's effective range to cover a calendar month **in full** (1st through last day) before it could govern that month at all — deliberately, to guarantee a monthly deliverable requirement is never silently prorated. A month only partially covered had **no governing version, full stop**. Real consequence: Mrinal's Agreement (effective 10 Sep 2026) could never govern September 2026, the one month with real activity.

### The user's design
*"reviews started from date of signed to that month end, if 15th then 15-30, next month 1 to 30 like that"* — the first reporting period should run from the Agreement's real effective date through that month's end; every later period reverts to a normal full calendar month.

### The fix
Added a narrowly-scoped **"inception exception"** to `coversMonth`: an Agreement's very **first version (version 1)** now also governs the **one** calendar month its own `effectiveFrom` falls inside, even though that month starts before `effectiveFrom`. Every other month — including that same version's later months, an ending/superseding mid-month, or any version after the first — still requires full whole-month coverage exactly as before. This is a one-time inception allowance, not a general partial-month rule.

### The open design question, and how it was resolved
The standing "never prorated" rule exists specifically so a monthly deliverable requirement (e.g. "20 pieces/month") is never silently scaled down. Rather than inventing a new day-based proration for the partial period, the fix deliberately changes **nothing else**:
- `monthlyDeliverableRequirement` stays the Agreement's full, unscaled monthly figure.
- The **already-existing** base-provision proration in `amount-determination.ts` (Step 15C: `serviceBase = fixed / required × min(actual, required)`) is what turns a short real window into a fair amount. No new money math was invented — the fix reuses a mechanism that already shipped.

**Correction (2026-09-30, closure-reconciliation pass) — the paragraph below is stale, kept only as history.** *~~The Partner Review's evidence window (`partner-reviews/period.ts`) is untouched — still the full calendar month — so the real `actualQualifyingCount` naturally reflects only what the Partner could realistically deliver in the shorter real window.~~* This was true of the original Step 14D fix only. A later re-audit (`policy-adapter.ts`'s own code comment: "Step 14D re-audit, remediation plan Wave B, finding #64") added `GoverningCommercialPolicy.evidenceWindowStart`, set to the Agreement's real `effectiveFrom` for exactly the same version-1 inception-month case `coversMonth` exempts — this is what actually narrows `evidence-collector.ts`'s Assignment/Analytics evidence-selection window for that one governed month, so pre-effective-date evidence is correctly excluded (`periodStart = max(calendarMonthStart, effectiveFrom)`, confirmed directly against current source during the 2026-09-30 fidelity audit). The deliverable *requirement* itself still stays the Agreement's full, unscaled figure — only the evidence *selection window* narrows, not the target.

Both were created **2026-09-29**, safely after the Agreement's 2026-09-10 effective date — so this fix carries zero risk of over-counting pre-Agreement activity for this real case. The residual edge case (an Assignment dated *before* the effective date but still within the same inception month) is documented in the code comment as a known limitation for future Partners, not silently ignored.

## 10b. Finding #50 reopened and re-fixed — canonical multi-record semantics restored

The Priority Defect Wave's #50 fix (§10 above) kept a pre-existing hard structural rule — exactly one canonical Content thread per Assignment, ever, enforced by a permanent `contentAssignmentThreadClaims/{assignmentRef}` claim doc — and adapted `requiredCount`'s own business meaning to fit it: "N required" became "N links inside that one thread's current revision." The user rejected this explicitly: **one Assignment carries the obligation count, and multiple qualifying Content *records* fulfill it** — never multiple links inside one record — and directed that the structural 1:1 lock be removed, not worked around. A follow-up spec (`CreatorOps_Reopen_50_Multi_Record_Assignment_Fulfillment.md`, supplied by the user) governed the corrected fix in full detail.

**Design decision.** Multiple links submitted in one call to the public submission page stay as one Content record (cross-posting one deliverable to several platforms). Multiple Content records instead arise across **separate submission cycles over time**: once an Assignment's current Content thread reaches a terminal status (APPROVED/CANCELLED), the next submission session creates a genuinely new, independent record. `requiredCount` is fulfilled by the count of the Assignment's APPROVED Content records — mirroring the Agreement-level `qualifyingUnit: "approved_content_thread"` concept already in `commercial-builder.ts`, one level down.

**What changed.** `content-service.ts`'s `resolveOrCreateContentThread` now re-points the claim doc at a new record once the previous one goes terminal, instead of reusing it forever (race-safe: the same Firestore-transaction pattern as before, generalized). `fulfillment-service.ts`'s `evaluateAssignmentFulfillment` counts APPROVED Content records across the whole Assignment (unbounded read — a gating decision, not a display surface) instead of hardcoding a single thread's link count; partial, exact and over-fulfillment are all reported honestly. A real, previously-dormant bug was found and fixed in the same pass: Partner Reviews' `evidence-builder.ts` kept threads in a `Map<assignmentRef, thread>` (singular) that would have silently dropped a second approved record from evidence and commercial qualification the moment the 1:1 lock lifted — fixed to aggregate every thread per Assignment, with a non-destructive `schemaVersion` migration (`normalizeStoredEvidenceSnapshot`) so already-stored FINALIZED/SUPERSEDED snapshots stay readable. The Assignment-side UI (`AssignmentContentPanel.tsx`, `AssignmentNextActionPanel.tsx`) and the Partner Reviews UI (`ReviewDetailTabs.tsx`) were both rewritten to list every Content record, not assume one. A second independent leftover from the earlier approach was caught during live browser verification and fixed: the public submission page still pre-filled `requiredCount` link rows and told Partners "Links required: At least N," the same wrong mental model baked into real Partner-facing copy — fixed to default to one row and say "N approved in total."

**Verification.** Full unit suite 4148/4148 (3 new tests proving the Payable-facing handoff correctly counts 2 approved records under one Assignment with a shape identical to a single-thread scenario, and that a cancelled record never counts). Full isolated real-Firestore emulator suite, run against a throwaway project distinct from both the app's default dev project and the persistent pilot (`demo-creatorops`, ports 18092/19092/19093/4092 — confirmed untouched throughout, per the standing rule that a same-project-id collision took down the pilot once already this program): 50/50 files, 1218/1218 tests pass. Live browser verification: a real Assignment with `requiredCount=2`, against its own isolated throwaway emulator + dev-server instance, driven through two full submit→approve cycles — captured "1 of 2 approved" with the Assignment still In Progress (not auto-completed early), both Content records listed together, and the final "2 of 2 approved" + auto-completed state.

Status: **CLOSED — ROOT CAUSE FIXED**, this time restoring the canonical multi-record semantics rather than redefining them around a structural limitation. Full detail (exact code changes, every test, closure-criteria checklist) is in `docs/REAL_DATA_PILOT_REMEDIATION_LEDGER.md`'s #50 row.

## 14. Finding #66's reporting-period timezone semantics — the user's explicit correctness requirement, proven

Before allowing #30/#66 to close, the user gave a concrete counter-example and required explicit proof: a post timestamped `2026-10-01T00:15:00+05:30` must not silently become a September post merely because its UTC instant falls on 2026-09-30, unless CreatorOps' reporting periods are explicitly defined in UTC.

**Investigation.** `partner-reviews/period.ts` was confirmed as this codebase's own existing, documented precedent: "every period boundary and every 'event date' in this module is a UTC calendar date... there is no local-timezone interpretation anywhere," via its `toUtcDate()` function (parse to instant, read the UTC calendar date). **A real bug found during this check, not assumed.** A zone-less ISO datetime string (no explicit `+HH:MM`/`Z`) parses via the native JS `Date` constructor as the **server process's own local time**, not UTC — confirmed by direct Node execution showing the identical input string resolving to different UTC instants under different `TZ` environment values. This is a documented general JavaScript gotcha this codebase had already worked around once before, in `metric-registry.ts`'s `parseSupportedDateTime` (explicitly appends `"Z"` when no zone is present). The new function was fixed to do the same.

**Proof delivered.** 14 boundary tests in `reporting-period.test.ts`, covering exactly the four categories the user required: a UTC timestamp at a month boundary, the user's own `+05:30` example (verified to correctly resolve to September, never October), a negative-offset timestamp crossing a UTC month boundary, and a timezone-less input under the established UTC-default rule. All 14 re-verified passing identically under both `TZ=Asia/Kolkata` and `TZ=America/Los_Angeles`, proving the result is genuinely independent of the server's own local timezone.
